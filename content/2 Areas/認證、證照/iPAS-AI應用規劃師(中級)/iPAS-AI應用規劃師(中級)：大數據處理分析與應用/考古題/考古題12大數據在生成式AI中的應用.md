#### LLM 查資料的三種架構怎麼選
| 架構 | 適合 | 不適合 |
|---|---|---|
| **RAG** | 從**文件**找答案（政策、手冊、合約） | 大量數值的**精確**加總、平均 |
| **Text-to-SQL** | 從**資料庫**算數字（營收、轉換率） | 非結構化文件 |
| 微調 | 改變模型的**語氣、格式、專業知識** | 經常變動的資料 |

> [!warning] 陷阱題
> 1. LLM 本身**不擅長算數**；需要精確統計時，讓 LLM **寫 SQL、交給資料庫算**。
> 2. **位置編碼**的作用是告訴 Transformer「誰在前、誰在後」，不是加雜訊、不是遮罩。

#### 115-1 Q36｜讓行銷人員用自然語言查資料湖
電商資料湖存放數百億筆點擊紀錄。要讓非技術背景的行銷人員用自然語言查詢（如「上個月台北市購買 3C 產品的女性轉換率為何？」），同時滿足高精確性、可擴展性、資料庫層級的權限控管與查詢審計，並確保結果由資料庫引擎精確執行。最適合哪種架構？
- (A) 協同過濾：根據歷史查詢推薦相似問題的答案，無法執行新問題的即時計算
- (B) RAG：讓 LLM 檢索相關資料後生成回答，但無法可靠執行大規模數值聚合與精確統計查詢
- (C) GAN：用於生成合成資料，不適合即時查詢與資料庫聚合運算
- (D) Text-to-SQL Agent：由 LLM 將自然語言轉為 SQL，交由分散式資料庫執行，兼顧自然語言彈性與查詢精確性

> [!success]- 點開看答案
> **答案：D**
>
> 「轉換率」需要對數百億筆資料做**精確的篩選與計算**，這是資料庫的強項。LLM 只負責把人話翻成 SQL，**計算交給資料庫**，權限控管和稽核也沿用資料庫既有的機制。
> 這題的選項很友善：(A)(B)(C) 自己就寫出了「無法」「不適合」。
>
> **PM 觀點**：Text-to-SQL 上線前要處理的風險：
> - LLM 寫錯 SQL 但結果「看起來合理」→ 要**顯示 SQL 讓使用者檢查**，或建立常用指標的**語意層（Semantic Layer）**。
> - 防止 LLM 產生 `DELETE`、`DROP` → 只給**唯讀權限**。

#### 115-1 Q35｜Transformer 位置編碼的作用
Transformer 文本分類模型對詞語順序的變化不夠敏感。位置編碼（Positional Encoding）的主要作用為何？
- (A) 在詞嵌入中加入隨機擾動，以提升泛化能力
- (B) 在注意力機制中加入遮罩，限制模型只能關注部分詞語
- (C) 將輸入序列轉換為可同時運算的向量表示，以提升計算效率
- (D) 在詞的向量表示中加入位置資訊，使模型能區分序列中不同位置的詞語

> [!success]- 點開看答案
> **答案：D**
>
> Self-Attention 是**同時**看所有詞，本身**不知道順序**，「狗咬人」和「人咬狗」對它來說一樣。位置編碼就是在每個詞的向量上加一個「**座位號碼**」。
> (B) 是**注意力遮罩（Mask）**，GPT 用它讓每個詞只看得到前面的詞。
>
> **補充**：原始 Transformer 用正弦／餘弦函數產生位置編碼；現在的 LLM（如 Llama）多用 **RoPE（旋轉位置編碼）**，對長文本的表現比較好。

#### 114-2 Q24｜多來源資料的生成式 AI 訓練處理
用大量客服紀錄與產品評論訓練語言模型，資料包含非結構化文字、影像與表格。希望在不降低模型效能的前提下，提升資料處理效率與一致性，哪一種策略最適合？
- (A) 建立資料湖結構，以 Apache Spark 或 Ray 進行分散式資料預處理與特徵抽取，再串接至模型訓練管線
- (B) 採用單節點高效能伺服器搭配批次處理，集中執行資料清理與格式轉換
- (C) 將所有文字轉為向量，以資料庫索引方式直接餵入語言模型訓練
- (D) 用生成式模型先自動清理資料，再輸入下游訓練流程

> [!success]- 點開看答案
> **答案：A**
>
> 三個需求對應三個元件：**多種格式** → 資料湖；**大量、要效率** → 分散式處理（Spark 擅長表格與 ETL，**Ray** 擅長 Python 與 AI 工作負載）；**一致性** → 用 Pipeline 串起來，每次都跑同一套流程。
> - (B) 單節點撐不住大量資料。
> - (D) 讓 LLM 清理資料可以當輔助，但結果不穩定、成本高，不能當主要策略。
