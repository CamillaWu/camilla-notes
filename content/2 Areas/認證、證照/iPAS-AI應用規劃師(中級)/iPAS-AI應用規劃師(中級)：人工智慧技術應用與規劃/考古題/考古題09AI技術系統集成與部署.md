#### 上線策略比較
| 策略 | 真實使用者看到新模型嗎？ | 能量測業務指標嗎？ | 用途 |
|---|---|---|---|
| 影子模式 Shadow | ✗（只在後端跑） | ✗ | 驗證穩定性、比對輸出 |
| 金絲雀發布 Canary | ✓（1～5% 流量） | **✓** | 小流量驗證真實成效 |
| A/B 測試 | ✓（分組） | ✓ | 比較兩版本成效 |
| 漸進式部署 Phased | ✓（逐步放大） | ✓ | 從小到大擴量 |
| 藍綠部署 Blue-Green | 一次切換 | — | 快速切換與回滾 |

#### 監控指標：哪些是「預警」、哪些是「結果」
- **最早的預警**：**輸入分布漂移**（PSI、KL 散度）→ 不用等標註答案回來就能算。
- **中間訊號**：預測結果分布、置信度分布變化。
- **最終結果**：準確率、業務指標下降 → 通常要等標註回來，**發現時已經晚了**。

> [!warning] 陷阱題
> 1. **Kubernetes 管的是「容器的部署、擴展與運行」**，不負責訓練調參、資料版本或 GPU 運算本身。
> 2. **Model Registry＝模型版本的倉庫**（版本、訓練紀錄、部署狀態）；**Feature Store** 才管特徵版本；**監控工具**才追漂移。
> 3. **CI 的核心＝每次 commit 自動觸發建置與測試**，不是「每天固定時間手動合併」。
> 4. 只看**整體** RMSE 會掩蓋**少數群組**的錯誤 → 要**分群監控**。
> 5. 漸進式部署遇到問題，正確做法是**暫停擴量、修好再繼續**，不是直接全面上線，也不一定要完全放棄。
> 6. 上傳 5MB 影像用 **POST＋Request Body**，不能用 GET 放在 URL。

## Notes
### 一、MLOps 與 CI／CD
#### 115-1 Q22｜MLOps 的核心角色
金融科技公司希望實現「訓練 → 測試 → 部署 → 監控 → 再訓練」的自動化串接，並確保線上模型版本可追溯。MLOps 的核心角色為何？
- (A) 專注於訓練資料的標註與品質控管
- (B) 透過自動化模型搜尋與參數調整，降低開發門檻
- (C) 建立機器學習流程的自動化與版本管理機制，支援模型部署、監控與持續更新
- (D) 確保模型部署後維持穩定效能，減少後續維運與更新需求

> [!success]- 點開看答案
> **答案：C**
>
> MLOps＝把 DevOps 的精神用在 ML：**自動化＋版本管理＋持續監控與更新**。
> (B) 是 **AutoML**。(D) 錯在 MLOps 的目的是讓「**持續更新**」變得容易，不是「**減少**」更新。

#### 114-2 Q15｜Model Registry 的用途
MLOps 流程中，Model Registry 最常用於哪個階段？
- (A) 設定運算資源與執行環境
- (B) 建立可重複使用的資料與特徵版本
- (C) 集中管理模型版本、訓練紀錄與部署狀態
- (D) 追蹤模型上線後的表現與漂移

> [!success]- 點開看答案
> **答案：C**
>
> 把 Model Registry 想成模型的「**GitHub＋產品目錄**」：每個版本是誰訓練的、用什麼資料、目前在 Staging 還是 Production，都記錄在這裡。常見工具：**MLflow Model Registry**。
> (B) 是 **Feature Store**；(D) 是**模型監控**工具。

#### 114-2 Q29｜持續整合（CI）的核心實踐
AI 開發團隊要實施持續整合流程。哪一項做法最符合 CI 的核心實踐，且能減少整合風險？
- (A) 在主分支每日固定時間手動合併並執行完整測試
- (B) 每次程式碼提交後自動觸發建置、單元測試及靜態程式碼分析
- (C) 模型訓練完成後定期回顧並合併程式碼
- (D) 透過自動化部署腳本，在特定時間點批次釋出到測試環境

> [!success]- 點開看答案
> **答案：B**
>
> CI 的兩個關鍵字：**頻繁**（每次 commit）＋**自動**（不靠人手）。問題越早發現，修起來越便宜。
> (D) 講的是**持續部署（CD）**，不是 CI。

### 二、部署架構與系統設計
#### 114-2 Q13｜Kubernetes 的核心功能
下列何者為 Kubernetes 在 AI 模型部署與運行中的核心功能？
- (A) 自動化管理模型的訓練流程與參數調校
- (B) 管理與協調模型服務的部署、擴展與運行環境
- (C) 提供 AI 模型的資料儲存與版本控管
- (D) 負責深度學習推論的 GPU 加速運算

> [!success]- 點開看答案
> **答案：B**
>
> Kubernetes（K8s）是**容器的調度中心**：決定服務跑在哪台機器、流量大時自動多開幾份、掛掉時自動重啟。
> (D) GPU 加速是 **CUDA、TensorRT** 等的工作，K8s 只負責「把 GPU 分配給哪個容器」。

#### 114-2 Q31｜每秒一萬次請求的架構
每次推論約需 1 秒，必須支撐 **10,000 RPS**。為確保高可用並穩定應付流量峰值，最合適的架構為何？
- (A) 依賴單台超高效能伺服器垂直擴展
- (B) 容器化部署並水平擴展服務實例，結合自動彈性伸縮
- (C) 限制最大併發連線數
- (D) 增加批次大小，一次處理上千筆請求

> [!success]- 點開看答案
> **答案：B**
>
> 每次 1 秒、每秒 1 萬次 → 同一時間約有 **1 萬個請求在處理中**，一台機器不可能扛得住，只能**水平擴展**（加機器）。
> (A) 單台機器有上限，而且壞了就全掛（**單點故障**），不符合高可用。

#### 115-1 Q44｜上傳 5MB 影像的 API 設計
推論 API 要處理使用者上傳的高解析度影像（平均 5MB）並即時分類。HTTP 方法與資料傳輸格式的最佳實踐為何？
- (A) HTTP GET，影像 Base64 編碼後放在 URL Query String
- (B) HTTP POST，影像以 multipart/form-data 或 application/octet-stream 傳輸於 Request Body
- (C) HTTP PUT，透過 application/xml 傳遞影像
- (D) 要求客戶端下載模型在本地推論

> [!success]- 點開看答案
> **答案：B**
>
> - **GET** 用來「拿資料」，URL 長度有限制（通常幾 KB），塞不下 5MB。
> - **POST** 用來「送資料」，大檔案放在 **Request Body**。
> - **multipart/form-data** 是網頁上傳檔案的標準格式；**octet-stream** 是直接傳原始二進位。
>
> (C) PUT 語意是「更新資源」，XML 也不適合傳二進位影像。

#### 115-1 Q45｜外部服務逾時引發連鎖故障
平台整合語音辨識、NLP、知識圖譜等外部微服務，高峰時某外部服務偶發延遲或逾時，導致請求鏈路壅塞，最後整個平台中斷（Cascading Failure）。從架構層面預防，最有效的設計模式為何？
- (A) 改為同步串行處理並取消逾時限制
- (B) 為外部服務導入斷路器模式，異常時暫停呼叫並提供替代回應
- (C) 擴充各微服務的執行緒池上限
- (D) 停用服務健康檢查

> [!success]- 點開看答案
> **答案：B**
>
> **斷路器（Circuit Breaker）**就像家裡的電源保險絲：偵測到某服務連續失敗，就**先斷開**一段時間，直接回覆替代內容（如「暫時無法提供此功能」），不讓所有請求卡在那裡等。
> (A) 取消逾時＝讓請求無限等待，**正是**造成連鎖故障的原因。(C) 只是讓更多執行緒卡住。

### 三、推論與訓練效能
#### 115-1 Q24｜延遲測試的目標
即時詐欺偵測系統對回應時間有嚴格限制。上線前進行延遲測試（Latency Testing），主要評估什麼？
- (A) 推論過程中的記憶體使用量
- (B) 模型對異常或攻擊輸入的穩定性
- (C) 模型在不同族群上的預測是否一致
- (D) 從接收輸入到產生預測所需的回應時間是否符合系統要求

> [!success]- 點開看答案
> **答案：D**
>
> 送分題，**Latency＝延遲＝回應時間**。(A) 是資源測試、(B) 是穩健性／安全測試、(C) 是公平性測試。
>
> **實務**：延遲要看 **P95／P99**（最慢的 5%、1%），不能只看平均，否則少數很慢的交易會被平均值掩蓋。

#### 115-1 Q40｜邊緣裝置降低推論延遲
產線瑕疵檢測從雲端改到邊緣裝置推論，仍未達 200ms 要求。**不更換硬體**下，哪一組技術最能降低延遲並維持合理準確率？
- (A) 減少訓練資料量並重新訓練
- (B) 使用批次推論處理多張影像
- (C) 採用模型集成，多模型投票
- (D) 將模型由 FP32 量化為 INT8，並進行推論加速優化

> [!success]- 點開看答案
> **答案：D**
>
> **量化**：把每個權重從 32 位元浮點數改成 8 位元整數，模型變成約 **1/4 大小**、算得更快，準確率通常只掉一點點。
> (B) 批次推論提高的是**吞吐量**，但每張影像要等湊滿一批，**單張延遲反而變長**。(C) 多個模型一起跑，**更慢**。(A) 訓練資料多寡不影響推論速度。
>
> **工具**：TensorRT、ONNX Runtime、OpenVINO（Intel CPU）。

#### 115-1 Q41｜GPU 使用率只有 60% 且有閒置間隔
單一 GPU 伺服器提供多租戶推論服務，GPU 使用率長期約 60%，kernel 之間有明顯閒置間隔，單次推論多為小批次；尖峰時延遲明顯波動。CPU、記憶體未達瓶頸，已排除硬體、網路與併發控制異常。最可能的原因為何？
- (A) GPU 排程策略與批次大小設定不當，導致運算單元未被有效利用
- (B) 請求併發控制不佳，多個請求搶占 GPU Context
- (C) GPU 硬體效能不足
- (D) 模型未量化，推論成本過高

> [!success]- 點開看答案
> **答案：A**
>
> 用排除法：題目已排除**硬體**（C）與**併發控制**（B）；GPU 只用到 60% 代表**算力根本沒用完**，所以不是模型太重（D）。剩下的就是「**一次送太少工作給 GPU、而且送得斷斷續續**」。
>
> **業界做法**：**動態批次（Dynamic Batching）**，把短時間內進來的請求湊成一批再送 GPU，常見工具是 **NVIDIA Triton Inference Server**、**vLLM**（LLM 專用的連續批次）。

#### 114-2 Q37｜多 GPU 訓練記憶體不足
大型語音合成模型以多台 GPU 訓練，常出現 GPU 記憶體不足。模型架構固定、無法換硬體，要在維持效能與收斂品質下降低**單張 GPU** 的記憶體壓力，哪一種方法最有效？
- (A) 減少訓練資料量
- (B) 採用較小的批次大小，並搭配資料分片分散訓練負載
- (C) 增加學習率以加快收斂
- (D) 改用測試資料集進行部分訓練

> [!success]- 點開看答案
> **答案：B**
>
> 批次越小，每次放進 GPU 的資料越少，**記憶體佔用就越低**；資料分片讓每張 GPU 只處理自己那一份。
> (A) 資料總量不影響單次記憶體；(D) 用測試集訓練是**資料洩漏**。
>
> ⚠️ **業界做法補充**：批次太小會讓梯度不穩、影響收斂。實務上會搭配**梯度累積（Gradient Accumulation）**維持等效批次大小，並使用**混合精度訓練（FP16／BF16）**、**梯度檢查點（Gradient Checkpointing）**，以及把模型參數分散到多張 GPU 的 **ZeRO／FSDP**。

### 四、上線策略
#### 115-1 Q43｜離線指標很好，上線前怎麼驗證真實成效
新版推薦模型離線 AUC、NDCG@10 都顯著優於現行模型，但離線測試無法反映真實互動。全面上線前，要在**可控制風險**下**量化真實業務指標**，應採用哪種線上驗證策略？
- (A) 影子模式：新舊模型同時預測，但只顯示舊模型結果
- (B) 回測：用歷史日誌模擬
- (C) 金絲雀發布：將 1～5% 流量導向新模型，量測 CTR、CVR 並逐步擴量
- (D) 負載測試後直接全面上線

> [!success]- 點開看答案
> **答案：C**
>
> 兩個條件同時滿足的只有金絲雀：「**風險可控**」（只影響 1～5% 使用者）＋「**能量測業務指標**」（使用者真的看到新推薦，才有點擊與購買）。
> (A) 影子模式使用者**看不到**新模型的結果，無法量測 CTR、CVR。

#### 115-1 Q47｜漸進式部署到 30% 時延遲上升
新推薦模型採漸進式部署，從 5% 逐步提升。初期轉換率略有提升，但流量提升至 **30%** 時延遲明顯上升，部分使用者體驗變差。最適當的下一步為何？
- (A) 立即全面部署至 100%，觀察整體效果
- (B) 還原至舊模型並停止新模型測試
- (C) 維持 30% 並持續觀察，暫不調整
- (D) 暫停流量提升，針對延遲問題做效能分析與優化後再繼續部署

> [!success]- 點開看答案
> **答案：D**
>
> 轉換率有提升，代表模型**有價值**；延遲變高，代表**系統撐不住這個流量**。所以是「**先停、修好效能、再繼續**」。
> (B) 放棄一個有價值的模型太可惜；如果延遲嚴重影響使用者，可以**先降回 5%**，但不必停止整個測試。

### 五、監控與漂移偵測
#### 114-2 Q32｜最能提早發現效能下滑的監控指標
模型已部署，希望透過監控指標**提前**偵測效能可能衰退。哪一項最具預測效力？
- (A) CPU 與記憶體使用率波動
- (B) 推論結果的置信度分佈變化趨勢
- (C) API 平均回應時間與延遲百分位數
- (D) 輸入特徵與訓練資料分布差異的 PSI 指數

> [!success]- 點開看答案
> **答案：D**
>
> **PSI（族群穩定性指數）**比較「現在進來的資料」與「訓練時的資料」分布差多少。資料先變，模型才會變差，所以它是**最早的預警**。
> 常用經驗門檻：**PSI < 0.1 穩定；0.1～0.25 需注意；> 0.25 顯著偏移**。
> (A)(C) 是**系統健康**指標，跟模型準不準無關。(B) 也有預警效果，但比輸入漂移晚一步。

#### 114-2 Q22｜確認資料分佈是否改變
顧客流失模型上線數月後準確率下降，懷疑顧客行為改變導致資料漂移。為了**偵測並確認**資料分佈是否變化，最合適的做法為何？
- (A) 定期重新訓練模型
- (B) 提升模型複雜度
- (C) 增加測試資料量
- (D) 計算輸入特徵分佈間的 KL 散度

> [!success]- 點開看答案
> **答案：D**
>
> 題目問的是「**偵測與確認**」，不是「**解決**」。**KL 散度**衡量兩個分布的差異，數值越大差越多。
> (A) 是**解決方法**，而且沒有先確認原因就重訓，可能白做工。
>
> **補充**：常見的漂移偵測統計量還有 **PSI、KS 檢定、Wasserstein 距離、JS 散度**。

#### 114-2 Q46｜MLOps 主動偵測分布偏移
線上流失預測模型準確率逐漸下降，系統正常、沒有錯誤訊息，分析發現輸入分布與訓練資料顯著偏移。要在 MLOps 流程中**主動偵測並預警**，最應採用哪項措施？
- (A) 建立即時的資料漂移與概念漂移監測機制
- (B) 將模型量化以降低延遲
- (C) 增加超參數調整次數
- (D) 使用固定隨機種子

> [!success]- 點開看答案
> **答案：A**
>
> 「系統正常、沒有錯誤訊息，但模型越來越不準」是 AI 系統特有的**靜默失效**，傳統 IT 監控抓不到，所以要另外建立**漂移監控**。
>
> **工具**：Evidently AI、Arize、WhyLabs、各大雲端平台的 Model Monitoring。

#### 115-1 Q42｜整體 RMSE 沒變但高額理賠誤差變大
理賠金額預測模型上線三個月，整體 RMSE 無明顯變化，但業務反映**高額理賠**的預測誤差明顯增加。高額案件只佔約 5%，監控機制沒有發現。最可能的設計缺陷為何？
- (A) 監控頻率不足，應改為即時串流監控
- (B) 高額理賠屬長尾分布，無法透過監控發現
- (C) RMSE 無法反映高額誤差，應改用 MAE
- (D) 僅監控整體 RMSE，未針對不同理賠金額區間分群監控

> [!success]- 點開看答案
> **答案：D**
>
> 5% 的樣本變差，被 95% 正常的樣本**平均掉了**。解法是**分群（Slice）監控**：依金額區間、地區、產品別分別看指標。
> (C) 方向反了：RMSE 因為有平方，**對大誤差反而比 MAE 更敏感**，換成 MAE 會更看不出來。
>
> **PM 觀點**：監控儀表板要針對**業務最在意的族群**（高價值客戶、高風險案件）單獨開一條指標。

#### 115-1 Q49｜不適合放在即時監控的指標
推薦模型的線上監控儀表板，下列哪一項**最不適合**放在即時監控系統，而應交給離線實驗追蹤系統管理？
- (A) 訓練實驗中每個 Epoch 的學習率變化曲線與超參數設定軌跡
- (B) 推論 API 的 P50／P95／P99 延遲與每日請求量
- (C) 輸入特徵分佈的 PSI，偵測資料漂移
- (D) 模型預測結果分佈與定期回收的人工標註結果之對比

> [!success]- 點開看答案
> **答案：A**
>
> 學習率曲線、超參數是**訓練階段**的紀錄，模型上線後就不會再變了，應該放在**實驗追蹤工具**（MLflow、Weights & Biases）。
> (B)(C)(D) 都是**上線後持續在變**的東西，才需要即時監控。
